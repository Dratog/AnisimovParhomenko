# Учебный стенд OpenTofu

OpenTofu создаёт сеть, том PostgreSQL, два образа и три контейнера: базу данных
и два SSH-сервера. При `server_count = 2` в состоянии должно быть семь ресурсов.
Приложения на SSH-серверы устанавливаются на следующих этапах курса.

## Подготовка

Нужны OpenTofu версии 1.10 или новее, работающий Docker и SSH-ключ.
На Windows выполняйте команды ниже в WSL с доступом к Docker Desktop.
Установка OpenTofu описана в [официальной инструкции](https://opentofu.org/docs/intro/install/standalone/).

```bash
tofu version
docker info
```

Если отдельного учебного ключа ещё нет, создайте его, не перезаписывая имеющиеся:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/praktikum_ed25519
```

Перейдите в `infra/terraform` и подготовьте локальные значения:

```bash
cp terraform.tfvars.example local.auto.tfvars
```

В `local.auto.tfvars` укажите путь к открытому ключу, например
`ssh_public_key_path = "~/.ssh/praktikum_ed25519.pub"`, и уникальное имя проекта.
Функция `pathexpand` раскрывает `~` перед чтением ключа. Приватный ключ
остаётся на компьютере и в образ не передаётся.

Проверьте свободные порты: SSH 2201/2202, будущие приложения 8101/8102 и порт
БД из `db_port`. В образце выбран 15432, чтобы не занимать обычный порт 5432.
Учебный пароль по умолчанию предназначен только для этого локального стенда.
Свой пароль можно передать переменной окружения `TF_VAR_db_password`.

## Создание и проверка

Все команды OpenTofu выполняются из `infra/terraform`:

```bash
tofu init
tofu fmt -check
tofu validate
tofu plan -out=stand.tfplan
tofu apply stand.tfplan
tofu state list
tofu output servers
```

На пустом стенде план показывает `7 to add, 0 to change, 0 to destroy`.
После применения `state list` содержит:

```text
docker_container.db
docker_container.server[0]
docker_container.server[1]
docker_image.postgres
docker_image.server
docker_network.stand
docker_volume.pgdata
```

Вывод `servers` содержит имя каждого сервера, `host = "127.0.0.1"`, SSH-порт
и порт приложения. Для `project_name = "praktikum"` проверьте контейнеры и SSH:

```bash
docker ps --filter name=praktikum-
ssh -i ~/.ssh/praktikum_ed25519 -p 2201 deploy@127.0.0.1
ssh -i ~/.ssh/praktikum_ed25519 -p 2202 deploy@127.0.0.1
tofu plan
```

Должны работать три контейнера; повторный план сообщает `No changes`.
Порты приложения зарезервированы, но API на серверах появится после его установки.

## Удаление и повторное создание

```bash
tofu destroy
tofu state list
docker ps -a --filter name=praktikum-
tofu plan -out=stand.tfplan
tofu apply stand.tfplan
tofu plan
```

Подтвердите удаление в интерактивном запросе. Удаление уничтожает учебную БД
в томе этого стенда. Сразу после него состояние пустое и контейнеров проекта
нет. Повторное применение создаёт те же логические семь ресурсов, а следующий
план снова сообщает `No changes`. Docker ID при этом могут отличаться.

## Локальные файлы

State, его резервные копии, каталог `.terraform`, локальные `*.tfvars` и планы
`*.tfplan` исключены из Git. Пример `terraform.tfvars.example` хранится
в репозитории без приватных значений.

State может содержать пароль даже при `sensitive = true`: этот признак скрывает
значение в обычном выводе команд, а сам файл требует защиты. Не публикуйте
`tofu output -json` целиком: в нём могут быть чувствительные outputs.

## Два независимых состояния

Для совместного эксперимента нужны два рабочих каталога с одинаковой
конфигурацией и одинаковыми значениями переменных, подключённые к одному
Docker daemon. Два независимых Docker на разных компьютерах создают два разных
стенда и конфликт владения одним стендом не демонстрируют.

Первый участник создаёт стенд, второй готовит копию только конфигурации,
контекста `infra/server-image` и локальных значений. State первого участника
во второй каталог не копируется. После `tofu init` второй `tofu plan` снова
предлагает семь ресурсов, поскольку его состояние пустое.

Локальная блокировка первого state не связывает второй файл состояния.
Последующее применение второй копии необходимо проводить совместно,
с фиксацией ошибок и частично созданных ресурсов. Возвращение к единственному
владельцу ресурсов проверяется планом без изменений в исходном каталоге.
Общее удалённое состояние и его блокировка относятся к следующему этапу курса.
